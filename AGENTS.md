# AGENTS.md — bank_api

## Estado real (el README describe el objetivo, no el código)
- `README.md` documenta JWT, PostgreSQL, transacciones y tests completos; el repo es un skeleton. Verifica `src/` antes de asumir que un endpoint existe.
- Entrada: `io.onstructive.micronaut.Application`; paquete base `io.onstructive.micronaut`.
- Stack verificado: Java 21 (`build.gradle.kts`), Micronaut 4.10.12 (`gradle.properties`), plugin Gradle 4.6.2, wrapper Gradle 8.14.3.
- Controllers: `AccountController` en `/api/accounts` (spec-03): `GET` (list), `POST` (create), `GET /{id}`, `DELETE /{id}`; IDs `UUID`; `ownerId` tomado del claim `userId` del JWT; `deposit`/`withdraw` retirados del controller (reimplementados en `/api/transactions`, spec-04). La ruta legacy `/accounts` ya no existe. `AuthController` en `/api/auth` (spec-02): `POST /register`, `POST /login`, ambos `@PermitAll`. `TransactionController` (spec-04), base `@Controller("/api")`: `POST /api/transactions/deposit`, `POST /api/transactions/withdraw`, `POST /api/transactions/transfer` (201 `TransactionResponse`) y `GET /api/accounts/{accountId}/transactions` (200, historial en ambos sentidos). `@Secured` + `@ExecuteOn(IO)`; dueño siempre desde el claim `userId` del JWT. `TransactionService` usa `@Transactional` por operación: fondos insuficientes o cuenta ajena hacen rollback (balances intactos, sin fila de `Transaction`). Cuenta ajena/inexistente → 404; fondos insuficientes → 400; sin token → 401.
- Errores (spec-05): excepciones de dominio en `exception/` (`BankException` + `AccountNotFoundException`, `InsufficientFundsException`, `DuplicateResourceException`, `BusinessRuleException`). `GlobalExceptionHandler` (y `ValidationExceptionHandler`, que `@Replaces` el handler de validación de Micronaut) devuelven un **payload único** para `/api/**`: `{ "error", "message", "path", "timestamp", "fieldErrors"? }`. Los controllers ya no traducen excepciones con `try/catch`. Tabla de códigos: 400 validación (`VALIDATION_ERROR`, con `fieldErrors`) / regla de negocio (`BUSINESS_RULE_VIOLATION`, `INSUFFICIENT_FUNDS`); 401 autenticación (filtro de seguridad; ambos endpoints de `/api/auth/**` usan el payload único, con `AUTHENTICATION_FAILED` en credenciales inválidas); 404 inexistente/ajeno (`NOT_FOUND`); 409 duplicado (`CONFLICT`); 500 inesperado (`INTERNAL_ERROR`, mensaje genérico, **sin stack trace**); 429 exceso de peticiones (`RATE_LIMIT_EXCEEDED`, spec-07). Requiere `micronaut-validation` + `micronaut-validation-processor` en `build.gradle.kts`: sin ellos `@Valid` es no-op.
- Seguridad **activada** (spec-02, propiedad en spec-03): `micronaut.security.enabled=true` + `micronaut-security-jwt`, HS256 con `JWT_SECRET` (default solamente de desarrollo en `application.properties`, ≥32 bytes). `/api/auth/**` es público (`@PermitAll`); `/api/accounts` y `TransactionController` (`/api/transactions/**` y `/api/accounts/{accountId}/transactions`) llevan `@Secured(SecurityRule.IS_AUTHENTICATED)` y filtran siempre por el `userId` del JWT (sin este annotation Micronaut Security responde 403 incluso con token válido). Las reglas `intercept-url-map` de Swagger siguen anonymous. Hash de contraseñas BCrypt 10 rondas (`$2a$`/`$2b$`), nunca texto plano.
- Persistencia (spec-01): PostgreSQL 15 en Podman rootless en `127.0.0.1:5432` (db `bank_api`, usuario `bank_user`, password `bank_pass`). Los tres repositorios fijan `Dialect.POSTGRES`. **`datasources.default.schema-generate=NONE`**: Flyway es el único dueño del esquema (`V1__CreateTables.sql`, `V2__AddIndexes.sql` en `src/main/resources/db/migration/`).
- Swagger UI: `/swagger-ui.html` y `/swagger-ui/**` (recursos `classpath:META-INF/swagger`), ambos anonymous; el YAML se sirve en `/swagger/**`. El spec generado vivo está en `build/classes/java/main/META-INF/swagger/bank-account-api-1.0.yml`. `src/main/resources/openapi/bankaccount-0.0.yml` es un placeholder obsoleto (solo `/bankaccount`): no es fuente de verdad. `AuthController` está anotado con `@Tag`/`@Operation` para que registro y login aparezcan documentados (spec-06).
- Observabilidad (spec-06): `micronaut-management` publica `/actuator/health` con `status=UP` y `details` (indicador de disco `diskSpace`, JDBC bajo `jdbc` con detalle interno `database`). `details-visible=ANONYMOUS` hace visibles los detalles sin token. `HealthController` público en `/health` devuelve `{"status":"UP"}`. Logs JSON por línea con Logstash encoder (`timestamp`, `level`, `logger`, `message`, más `@version`, `thread`, `level_value`) configurado en `logback.xml`.
- Rate limiting (spec-07): `filter/RateLimitFilter` (`@Filter("/api/**")`, orden `SECURITY.after()` para leer el `Authentication` del JWT) usa contadores en memoria por ventana fija: IP/minuto, usuario autenticado/hora y peticiones de transacciones/minuto; el bucket de transacciones cubre **tanto** `/api/transactions/**` **como** el historial `GET /api/accounts/{accountId}/transactions`, y ambas rutas comparten el mismo contador (de IP o de usuario), por lo que suman sus peticiones al mismo límite. Defaults en `application.properties`: `ratelimit.enabled=true`, `ratelimit.per-ip.minute=100`, `ratelimit.per-user.hour=1000`, `ratelimit.transactions.minute=10` (valores del README). Al superarse → 429 con el payload único y `error=RATE_LIMIT_EXCEEDED`. La IP se resuelve de `X-Forwarded-For` (cabecera estándar tras proxy; fallback al socket). En tests `src/test/resources/application-test.yml` fija `ratelimit.enabled=false` para no alterar los 32 tests previos; `RateLimitTest` lo reactiva con `@Property` y límites pequeños. **Desviación:** los contadores son en memoria, por instancia, se reinician al arrancar y no se comparten entre réplicas.
- Cobertura (spec-08): plugin JaCoCo (`toolVersion=0.8.13`) con `jacocoTestReport` (HTML + XML) y `jacocoTestCoverageVerification` (mínimo 70% de líneas, regla `BUNDLE` sobre todas las clases de `io.onstructive.micronaut.*`). Cobertura real 2026-11-25: **90.24% líneas, 93.74% instrucciones, 75.00% ramas**. Reporte en `build/reports/jacoco/test/html/index.html`. **Desviaciones:** Testcontainers no usado (se comparte el contenedor Podman `bank-api-db`) y REST Assured no usado (se usa `Micronaut HttpClient`).
- Empaquetado (spec-09): `Dockerfile` multi-stage — etapa build `eclipse-temurin:21-jdk` ejecuta `./gradlew --no-daemon --console=plain shadowJar`; etapa final `eclipse-temurin:21-jre`, usuario no root `bankapi`, `EXPOSE 8080`, `ENTRYPOINT java -jar /app/bankaccount.jar`. `.dockerignore` excluye `.git`, `.gradle`, `build/`, `.idea/` y similares. JAR: `build/libs/bankaccount-0.1-all.jar` (~25 MB). Imagen construida: `localhost/bank-api:spec09` (~400 MB). `application.properties` añade `micronaut.server.port=${SERVER_PORT:8080}` (el Dockerfile fija `SERVER_PORT=8080`). Smoke test verificado: contenedor temporal `--rm --network host` + `GET /health` → 200 `{"status":"UP"}` + `podman stop`. **Desviaciones:** `./gradlew nativeImage` no ejecutado (GraalVM no instalado; se distribuye JVM fat JAR, no binario nativo); la app dentro del contenedor necesita alcanzar `bank-api-db` en `127.0.0.1:5432`, por eso el smoke test usa `--network host` (en producción hace falta una red compartida o `BANK_DB_HOST` apropiado).

## Spec Driven Development (SDD) — reglas obligatorias
1. Toda implementación se divide en specs secuenciales `00, 01, …`; **un sub agente por spec**.
2. Cada spec vive en `specs/NN-spec/` y contiene solo `spec-NN.md` (objetivo, alcance, criterios de aceptación verificables, comandos, DoD) y `agent.md` (rol del agente, archivos permitidos, prohibiciones, formato de reporte).
3. Spec corta y atómica: un objetivo, un agente, un commit. Si crece, se parte en dos.
4. El sub agente **no commitea**: implementa, corre la prueba corta y reporta diff + incidencias.
5. El orquestador verifica el resultado y lo muestra al usuario; **no avanza sin aprobación explícita**. Si no aprueba, el mismo agente corrige.
6. Un commit por spec, tras la aprobación, con Conventional Commits: `<type>[<scope>][!]: <descripción>`. Tipos: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `style`, `build`, `ci`, `chore`, `revert`. `!` o footer `BREAKING CHANGE:` para cambios rupturistas. `update` y `feature` no son tipos válidos → usar `refactor`/`docs` y `feat`. Ejemplo: `feat(auth): registro y login JWT (spec-02)`.
7. Tras cada spec: prueba corta en CPU (`./gradlew test` o el subconjunto), resultado visible e incidencias listadas; toda desviación se documenta en `NOTES.md`.
8. Prohibido: `push`, `reset`, borrados y tocar specs ajenas. Ante un bloqueo, detenerse y reportar.
9. Las specs se ejecutan en orden; las dependencias entre ellas son explícitas.
